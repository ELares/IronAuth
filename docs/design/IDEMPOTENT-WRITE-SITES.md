# Idempotent write sites

Every admin handler that requires an `Idempotency-Key`, and every same-crate `async fn`
those handlers call, is inventoried in `docs/design/idempotent-write-sites.txt`,
generated by `scripts/idempotent-write-audit.sh`. The number beside each is how many
store WRITE entry points that ONE FRAME reaches. **Every row with more than one must
appear in the table below with a verdict, and every name in that table must be a row the
inventory currently flags**, or the scan fails. The second half is what stops a verdict
from outliving the site it judges.

## The invariant

> A handler that requires an `Idempotency-Key` performs its data change, its audit
> row(s) and the Idempotency-Key record in ONE store transaction.

## Why (issue #247)

Two un-joined store writes behind one `Idempotency-Key` is a hole no reviewer sees from
the diff. The idempotency record commits with exactly one of the writes, so a failure
between them leaves a partial state the replay store cannot see, and the retry under the
same key is wrong in one of two ways:

- if the record did NOT commit, the retry re-executes against rows that already exist
  and answers a conflict that describes nothing the caller did;
- if the record DID commit, the retry replays a stored response for work that never
  finished, and no number of retries under that key will ever finish it.

Neither is a security hole on its own: the uniqueness constraints still hold, so nothing
is ever created twice. What breaks is the idempotency contract, and the residue is
recoverable only by an operator or by a fresh key.

Both live instances found by issue #247 are joined now:

- `invitations::create_invitation` provisioned the `pending_verification` user in one
  transaction and wrote the invitation (carrying the Idempotency-Key record) in a second.
  A failure of the second left an orphaned user, so the retry hit the identifier unique
  violation and answered **409**, and the identifier stayed wedged behind the ghost until
  an operator deleted it. It is one `ActingInvitationRepo::create_with_user` call now.
- `recovery_approvals::decide` committed the decision AND the Idempotency-Key record and
  then completed the recovery in a second transaction whose result it discarded. A failed
  completion stranded the flow, and the retry replayed the stored 200 without ever
  re-attempting the completion. `ActingRecoveryApprovalRepo::approve` does both now.

Joining is necessary and not sufficient. Both joined paths write the Idempotency-Key
record FIRST inside their one transaction, which changes nothing about what commits and
everything about what a CONCURRENT same-key request is told: written last, the loser blocks
on a data unique index and surfaces the conflict for that data (on the invitation path, a
409 naming the caller's own identifier as taken, MEASURED over HTTP), while written first
it blocks on `idempotency_keys`, reaches the idempotency conflict, and replays the winner's
committed response.

## What the count is, and is not

It is a **count, not a proof**, exactly like the session-mint and user-token-mint
registries. Two mutually exclusive arms count as two and are not a defect. What the count
guarantees is that a handler cannot GAIN a second store write without its author
regenerating the inventory and writing down why, which is the thing that did not happen
for four milestones at the two sites above.

It counts five spellings, because a rule defeated by a spelling rather than by a
decision is not a rule. The last two were closed after a MEASUREMENT that the first
version of the scan reported clean under each:

- an inline `.acting(` chain, the entry point to every mutating repository;
- each EXTRA use of a bound acting handle (`let acting = ...acting(...);` then two calls
  on it), which a naive count would see once;
- `.idempotency()`, the two-phase form that writes the record itself with no acting chain
  at all;
- `pub(crate) async fn` and a bare `async fn`, not only `pub async fn`. A two-write
  handler spelled `pub(crate) async fn` produced NO inventory row at all and the scan
  reported clean;
- a handler in a SUBDIRECTORY of the crate. The source glob was not recursive, so a
  two-write handler moved into `src/sub/` was never opened and the scan reported clean.

And the verdict requirement itself was two spellings away from meaning nothing. It was a
substring search over the whole document, so deleting the entire table below and leaving
two bare backticked mentions passed clean; and it ran in only one direction, so appending
a verdict for a handler that never existed passed clean too. A verdict is now a TABLE ROW
that names the site AND states a bold, shouted judgement, and every name the table carries
must answer to a row the inventory currently flags.

## What the count does NOT see: a write one frame away

The number on a row is that frame's own writes. A write performed by a HELPER the handler
calls belongs to the helper's row, not the handler's, so a handler with one write of its
own and one more inside a helper it calls is **not flagged**. This is a stated limit, not
an oversight, and the alternative was measured and rejected: `sudo.rs`'s
`require_fresh_privilege` holds a real `.acting(...).admin_sudo_elevations()` write on its
refusal path, and most of the handlers in the inventory call it, so summing helper frames
into every caller would flag nearly the whole registry with one identical verdict and bury
the rows that say something. (That particular write is on a path that short-circuits into
a refusal, so it is not a live atomicity defect; it is simply the reason summing is the
wrong shape.)

What the registry does instead is inventory every helper a listed handler calls as a row
of its own. So a helper that gains a SECOND write is flagged on its own row, and a handler
that starts calling a new helper changes the inventory and cannot be committed without
regenerating it. The one shape that shows only as a DIFF rather than as a FLAG is exactly
one write here plus exactly one write one frame away, and the diff is what forces the
author to look.

## Verdicts

| Site | Writes | Verdict |
| --- | --- | --- |
| `recovery_approvals.rs:decide` | 2 | **CLEAN.** One BOUND acting handle used twice, in the two arms of `match decision`: approve XOR reject. Exactly one runs per request, and each is a single joined store call that carries the Idempotency-Key record. The count sees two uses and cannot see the exclusivity; that is what this row is for. |
| `signing_algorithm.rs:set_client_signing_algorithm` | 2 | **STRUCTURALLY SPLIT, harm bounded.** The two writes are on two DATABASE ROLES: `clients.id_token_signed_response_alg` is data-plane writable only (the control role holds no grant) and `idempotency_keys` is control-plane writable only, so no single transaction can span them. The harm the invariant exists to prevent is BOUNDED rather than absent, because both writes are pure functions of the request: the column is set to a value derived only from the body, and the stored response body names only the client and that same algorithm. So on an UNDISTURBED retry the split self-heals: the retry under the same key finds no record, re-executes to the identical committed state, and stores the identical body, and because `ActingClientRepo::set_id_token_signed_response_alg` is a CHANGE-ONLY write (`... IS DISTINCT FROM $1 RETURNING id`), a same-value retry matches no row and writes no second audit row. **What it does not survive is another operator writing in between.** MEASURED: pin `RS256` under key A, lose the record, pin `ES256` under key B, then retry A. The retry re-executes against a column that has moved, so it writes a SECOND audit row and silently REVERTS the later operator's pin (`a_retry_after_a_lost_idempotency_record_reverts_a_later_pin_and_audits_again` in `crates/ironauth-admin/tests/signing_algorithm.rs` pins exactly that sequence). Neither half is a security hole, and the revert is reconstructable from the audit log rather than invisible, which is why the verdict is still DO NOT JOIN: joining would require a migration granting the control role a column-scoped `UPDATE (id_token_signed_response_alg)` on `clients` plus a control-role RLS policy, a deliberate widening of the plane separation and an owner decision rather than a drive-by. |
