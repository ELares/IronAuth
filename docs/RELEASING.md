# Releasing

IronAuth is a monorepo with independently versioned artifacts. Every release
names exactly one artifact; there is no repo-wide release train, so an urgent
server security release never drags SDK churn along, and vice versa.

## One version scheme

An artifact release is a git tag `<artifact>-vX.Y.Z` where `<artifact>` is the
artifact's name in docs/COMPATIBILITY.md (generated by
scripts/compat-matrix.sh; CI fails if it is stale) and `X.Y.Z` equals the
version in that artifact's manifest at the tagged commit. The release workflow
verifies the equality and refuses to run on mismatch. There are no other
version identities: no marketing versions, no module-path versions that
diverge from tags. A version referenced anywhere (advisory, changelog, docs)
is always the manifest version of one named artifact.

Current artifact lanes:

- `ironauth-vX.Y.Z`: the server binary. Produces a static musl binary, a
  CycloneDX SBOM, GitHub build provenance attestations, a GitHub release with
  the crate's changelog section, and a cosign-signed container image on GHCR
  (`.github/workflows/release.yml`).
- Library crates (`ironauth-env`, and later crates) release to crates.io under
  their own `<crate>-vX.Y.Z` tags once their APIs stabilize; until then they
  version inside the workspace only.
- TypeScript artifacts (SDKs, admin SPA, hosted pages) get their own lanes
  when the first package lands (see packages/README.md).

## Changelogs

Every artifact keeps its own `CHANGELOG.md` next to its manifest with a
section per released version, newest first, and an Unreleased section that
release PRs must update. The release workflow extracts the tagged version's
section as the release notes.

## Security advisory format

Every security advisory (GitHub Security Advisory and the release notes entry)
must name, without exception:

1. **Artifact**: the exact artifact name from docs/COMPATIBILITY.md.
2. **Affected versions**: a closed version range per artifact, for example
   `ironauth >= 0.3.0, < 0.7.2`.
3. **Patched version**: the first version containing the fix, per artifact.
4. **Severity**: CVSS score plus a one-line plain-language impact statement.

Advisories that touch multiple artifacts list every (artifact, range, patched)
triple separately. "Update to the latest version" without a named version
range is not an acceptable advisory body. Security-relevant fixes are also
called out with severity in the release notes of the patched release, never
silently included.

## Release checklist

1. PR updating the artifact's manifest version and its `CHANGELOG.md`
   (moving Unreleased content under the new version heading).
2. Merge on green; tag `<artifact>-vX.Y.Z` on the merge commit; push the tag.
3. The release workflow runs verify, build, SBOM, attest, release, and the
   image lane; check all lanes finished and the release page lists the
   binary, SHA256SUMS, and SBOM. The image lane verifies its own signature
   before finishing (see "Verifying a published image" below), so a green
   image lane means the published signature is checkable, not merely made.
4. First-time note: the release lane is validated end to end by the first
   real release; until then treat it as authored but unproven.
5. Record a HUMAN-TIMED quickstart run per guide in `docs/dx/timed-runs.md`.
   See below: this is DX evidence, and deliberately not a gate.

## The DEB

`cargo deb -p ironauth` builds a package carrying the binary, a systemd unit, and an
`/etc/ironauth/ironauth.toml` with `database.url` commented out. The release lane builds it
from the same build as the tarball rather than a second compile, and attests provenance for
both. The two are not byte-identical: cargo-deb strips the binary it packages, which is what
a package should ship.

Installing it does NOT start the service, and the reason is sharper than "nothing would
happen". With `database.url` absent IronAuth falls back to its built-in default of
`postgres://ironauth@localhost:5432/ironauth`, so an unconfigured server does not sit idle:
it tries a local database that is probably not there, and could in principle be one that is.
The documented sequence is:

```
sudo dpkg -i ironauth_<version>_amd64.deb
sudoedit /etc/ironauth/ironauth.toml          # uncomment and set database.url
sudo -u ironauth ironauth migrate --config /etc/ironauth/ironauth.toml
sudo systemctl enable --now ironauth
```

The config file is a dpkg **conffile**, so an upgrade preserves an operator's edits rather
than overwriting the file that holds their database credential. `dpkg -r` leaves it in place
and `dpkg -P` removes it; CI asserts both, because a silent replacement is exactly the
failure `conf-files` exists to prevent.

The unit runs as a system user with no login shell, and its hardening mirrors the Helm
chart's pod security context line for line where systemd has an equivalent: non-root,
`ProtectSystem=strict` for the read-only root, `PrivateTmp` for the writable `/tmp` the
chart gives as an emptyDir, and an empty capability set. A deployment should not get a
weaker posture for choosing a package over a cluster.

### Upgrading

The package does NOT restart the service on upgrade (`restart-after-upgrade = false`). The
default would stop the old binary and start the new one against the PRE-UPGRADE schema with
no migrate step between them, and a new binary meeting an old schema is the failure the
expand-contract discipline exists to avoid. Upgrade as:

```
sudo systemctl stop ironauth
sudo dpkg -i ironauth_<version>_amd64.deb
sudo -u ironauth ironauth migrate --config /etc/ironauth/ironauth.toml
sudo systemctl start ironauth
```

Secrets that should not live in a config file go in `/etc/default/ironauth`, which the unit
reads through an optional `EnvironmentFile`.

CI installs the package on an ordinary runner, points it at Postgres, runs the migrate step
and starts the unit, and requires `/readyz` to answer while the unit is still active (issue
#151 criterion 5). The active check matters: without it a stale listener on the port would
answer for a unit that had already died.

## Verifying a published image

The container images are signed with [cosign](https://docs.sigstore.dev/) in
keyless mode, so there is no public key to distribute. What stands in for one is
the signing IDENTITY: the release workflow of this repository, as attested by
GitHub's OIDC issuer.

```
scripts/verify-image.sh ghcr.io/elares/ironauth@sha256:<digest>
```

To check that an image came from one SPECIFIC release rather than any release,
pass the tag:

```
scripts/verify-image.sh ghcr.io/elares/ironauth@sha256:<digest> ironauth-v1.2.3
```

Without cosign installed, or to verify from somewhere this repository is not
checked out, the script is a thin wrapper around:

```
cosign verify \
  --certificate-identity-regexp '^https://github\.com/ELares/IronAuth/\.github/workflows/release\.yml@refs/tags/ironauth-v[0-9]+\.[0-9]+\.[0-9]+$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/elares/ironauth@sha256:<digest>
```

Both constraints are required. The issuer alone would accept a signature from
any workflow in any repository on GitHub; the identity alone would accept a
certificate minted by an issuer an attacker controls.

**Reference the image by digest, not by tag.** The script refuses a tag for this
reason: verifying `:latest` verifies whatever `latest` pointed at during the
call, and a registry can move it afterwards. A digest names the bytes the
signature covers.

The release workflow runs this same script against each image immediately after
signing it, so the command above is one CI has executed rather than one written
down and assumed to work.

## Human-timed quickstart runs

CI runs every quickstart's documented commands on every push and enforces a
15-minute budget. That proves the guides WORK and says nothing about what they
feel like: a machine does not mistype a command, re-read a paragraph, or stop to
work out which of two things it was meant to install.

So each release also records a person walking one through, start to finish, and
the number that matters is wall clock from opening the guide to a successful
login.

**This is not the acceptance gate and must never become one.** The gate is the
scripted run. A timed run is one person on one machine on one day; treating it as
a pass/fail would make a slow laptop a release blocker and would tempt whoever
holds the stopwatch to skip the reading, which is the only part being measured.

Record it in `docs/dx/timed-runs.md` with the template there. Report what was
confusing even when the time was good: the time is the signal that something is
wrong, and the notes are the only thing that says what.
